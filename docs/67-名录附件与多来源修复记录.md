# 名录附件与多来源入库修复记录

日期：2026-10-20。对应要求：`docs/66-企业名录附件与多来源入库要求.md`。本轮在 `docs/64`、`docs/65` 已完成的基础上，只修复采集器必要路径；真实 28 来源、规范化数据包和 Codex 独立比对报告均只读使用，未覆盖、未重新生成。

## 一、修改文件

- `src/services/cea-collect-svc.mjs`
  - 新增 DOCX 识别与有界解包：仅当来源 `kind=official_docx`、URL 明确 `.docx` 或 content-type 为 WordprocessingML 时进入；仅在内存/临时目录处理，不改全局 PDF/OCR 服务。
  - 解包脚本使用 Python 标准库 `zipfile` + `ElementTree`，只读 `word/document.xml`；限制原件字节、`document.xml` 解压大小、ZIP 总解压大小、输出字符数与运行时间；拒绝无效 ZIP、缺 `[Content_Types].xml`/`word/document.xml`、路径穿越、宏部件（`vbaProject.bin`）、加密条目、DTD/实体声明和解压超限。子进程使用 `stdio:'ignore'` + 临时文件（受限环境不能用管道捕获输出），结束删除临时目录。
  - 山西等 `multipart/form-data` 包裹 PDF：只接受恰好一个、边界完整、`%PDF-` 开头且以 `%%EOF` 结束的 PDF 附件；多附件、截断、非 PDF、超限、异常边界均失败，不猜选其中一个。原始 HTTP 哈希继续作为快照/来源 identity；解码后的 PDF 载荷单独计算并记录哈希；落盘和 `parsePdfDocument` 使用载荷。
  - 名录采集仍每批最多 4 个来源，共享 deadline、并发/SSRF/预算限制不变；DOCX 解包和 PDF 解析都受批次 deadline 约束。
- `src/services/cea-parse.mjs`
  - `dedupeEntityRows` 由 Map 覆盖改为合并：同一信用代码跨表/跨节时合并明确行业标签（`、` 分隔）、每行出处与备注，不再只留最后一行。
  - HTML 表格解析增加 Word 分页续表规则：仅当前表无表头、上一表有明确表头、列数一致、首行序号连续且无相反新名录标题时复用上一表头；空表不打断续表，非空异常表或不同行业新标题会断开继承。
  - 表标题行业取值只取最后一个句号后的明确标题，避免公告句中的多行业列表（如“发电、钢铁、水泥、铝冶炼”）把分行业表标题误判为无法识别。
  - 对同一表内混合行业且没有独立行业列的情况，仅用无歧义的行业分类代码兜底（4411/4412→发电，3011→水泥，3110/3120/3130/3140→钢铁，3216→铝冶炼）；2511 等仍不映射。
  - 修复真实 PDF 换行名称：吉林行尾独立“自备电厂”备注不再拼入企业名；广东跨行公司名前的右侧“自备”空格不再使名称片段因长度阈值被丢弃；深圳“南山热电厂/东部电厂”等合法名称后缀继续合并。
- `src/services/cea-svc.mjs`
  - 新增 `cea_entity_membership` 成员关系/出处读写：`entity_id + source_code + sector` 唯一，保留 `source_url`、`source_hash`、`snapshot_id`、`note`、创建/更新时间；同源同行业重采幂等。
  - `upsertCeaEntity` 对带 `source_code` 的输入保留本来源行业成员关系，其他来源不删除；主体 `sector` 按全部成员关系合并（如“发电、钢铁”）；没有来源的既有编辑路径保持兼容。
  - `listCeaEntities` 行业筛选改为命中主体 `sector` 或成员关系；返回 `source_memberships`；企业 `total` 仍按主体（信用代码+年度）计数。
  - 同源 hash 缓存命中改为按本来源成员关系去重企业计数，不再依赖主体最后一次 `source_code/source_hash`。
  - 省名筛选支持明确等价名（山西/山西省、重庆/重庆市、内蒙古/内蒙古自治区等），只做整名替换，不做任意 LIKE 模糊匹配。
  - 实体 CSV 增加 `notes` 列，包含全部成员关系行业与官方链接。
- `src/db/schema-cea.sql`
  - 纯增量新增 `cea_entity_membership` 表、唯一索引和来源/行业索引，不修改既有企业表字段。

## 四、限制与未做事项

- 当前 profile 未提供 GraphFlow MCP 工具（工具列表无 `mcp__graphflow__graphflow_*`），本机也没有可用的 `graphflow` CLI，因此未调用 `graphflow_context` 或 `graphflow_report_outcome`；在此如实记载，未伪造调用结果。
- DOCX 解包依赖本机 Python 标准库（Windows `python`、Linux 默认 `python3`，可用 `CCER_PYTHON` 显式指定）；未安装 Python 时如实登记 parse gap，不把 DOCX 当 HTML。仅支持 `.docx`（含 `word/document.xml`），不支持旧 `.doc`、宏文档或多附件 DOCX。
- DOCX 原始字节目前只通过 `source_snapshot` 的内容哈希/字节数留痕，未像 PDF 一样另存原件文件；解析 HTML 只在内存/临时文件中存在。若后续要求长期保存 DOCX 原件，可复用同一有界落盘策略。
- 山西外壳只支持单个完整 PDF；未扩大为任意 multipart 附件选择，也未改动全局 PDF/OCR 服务。
- 未执行真实网络采集、真实数据库导入、生产/预览库写入、部署或 GitHub 推送；真实 28 来源的入库和云端验收仍由 Codex 独立执行。
