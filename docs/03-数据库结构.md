# 数据库结构

本应用的结构化存储完全建立在 **SQLite** 之上，通过 Node.js 内置的 `node:sqlite` 模块提供的 `DatabaseSync` 同步接口访问（见 `src/core/db.mjs`），**零第三方依赖**：不需要 `better-sqlite3`、`sqlite3` 或任何 ORM，`package.json` 中没有数据库相关依赖项。数据库文件默认落在 `data/ccer.db`（可用环境变量 `CCER_DB_PATH` 覆盖，见 `DEFAULT_DB_PATH`），首次打开时若目录不存在会自动创建。每次建立连接时 `getDb()` 都会显式执行 `PRAGMA foreign_keys = ON`，并尝试设置 `PRAGMA journal_mode = WAL`（WAL 是写入数据库文件的持久属性；内存库不支持 WAL，此时被 `try/catch` 忽略）。这两条 PRAGMA 同样写在 `src/db/schema.sql` 的首部，因此任何直接执行 schema 的场景行为一致。建表全部使用 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，`migrate()` 在每次取连接时重放一遍 `schema.sql` 后读取 `system_meta.schema_version` 补齐版本号，因此 DDL 是幂等的；初始化与参考数据重建由 `src/services/seed.mjs` 的 `seedAll()` 负责。

## 设计约定

以下约定是 schema 的硬约束，不是可选建议。**写库代码必须遵守，评审时必须逐条核对。**

### 1. 所有实体有稳定 ID，报告引用「运行快照」而非最新库值

- ID 由 `src/core/util.mjs` 的 `newId(prefix)` 生成，格式为 **`前缀-<36进制时间戳>-<8位随机段>`**：`Date.now().toString(36).padStart(9, '0')` 保证时间有序（可按 ID 粗略排序），`randomUUID()` 去掉连字符后取前 8 位作为随机段保证唯一。所有实体表的 `id TEXT PRIMARY KEY` 都是这个格式。
- 各表的 ID 前缀：`SRC`（source_document）、`CHG`（source_change）、`MV`（methodology_version）、`RUL`（rule）、`FRM`（formula）、`FAC`（factor_version）、`PRJ`（project）、`EVD`（project_evidence）、`FCT`（project_fact）、`MCH`（match_run）、`ELG`（eligibility_run）、`CAL`（calculation_run）、`RPT`（report）、`RVW`（review_decision）、`ALR`（alert）、`SUB`（subscription）、`AUD`（audit_log）。
- 例外（有意为之，不违反本约定）：`fact_field.key`、`system_meta.key` 是自然键主键（字段字典与元数据本身没有生命周期，用键本身作标识更利于跨版本复用）；`app_user.id` 是内置固定字面量（`user-admin`、`user-researcher` 等），便于在种子数据与授权判断中稳定引用。
- **报告不读「最新库值」**：`report.snapshot_json` 只保存 `eligibility_run_id`、`match_run_id`、`calculation_run_ids`、`methodology_version_id`、`analysis_base_date` 这组指针，`report.content_json` 保存装配完成的正文全文；数值与因子取值来自 `calculation_run.result_json` / `factor_snapshot_json`，而不是重新查询 `factor_version` / `methodology_version` 的当前值。方法学版本以「一行一个版本」的方式存放而不是就地更新，因此历史版本行永远存在（详见 `## 数据保留与版本快照`）。

### 2. 正式发布 / 征求意见 / 修订 / 废止分列存储，永不互相覆盖

`methodology_version.document_status` 取值为 `formal`（正式发布）、`draft`（征求意见稿）、`revised_draft`（修订征求意见稿）、`repealed`（已废止），并且**同一 `methodology_id` 的每个版本各自占一行**：`methodology_version` 上的 `UNIQUE(methodology_id, version)` 保证版本行不重复，`supersedes_id TEXT REFERENCES methodology_version(id)` 用自引用把「修订稿 → 现行正式版」串成链条，`repeal_date` 记录废止日期。新版本发布时**新增一行**，绝不 `UPDATE` 旧行的 `document_status`，所以「某年某月当时生效的是哪一版」可以被完整复原。判断引擎据此分流：只有 `document_status = 'formal'` 且 `is_candidate_eligible = 1` 且 `rulecard_status = 'approved'` 的版本才进入「可申报候选」，草案只进 `observations`（见 `src/services/engine.mjs` 的 `runMatch`）；`runCalculation` 在 `document_status !== 'formal'` 时直接返回 409 拒绝出数。

### 3. 注册登记链条的六个状态各占一个独立布尔列，禁止合并为一个状态字段

`project` 表用六列 `INTEGER NOT NULL DEFAULT 0` 分别承载链条上的六个节点，**不设统一的 `registry_status` 字段**：

| 列 | 含义 |
|---|---|
| `registry_project_public` | 项目公示 |
| `registry_validated` | 审定 |
| `registry_project_registered` | 项目登记 |
| `registry_reduction_public` | 减排量公示 |
| `registry_verified` | 核查 |
| `registry_reduction_registered` | 减排量登记 |

原因：链条节点可能并存、可能跳步、也可能出现「已登记但未核查」的异常组合，单一枚举一律会丢信息。展示层只做读取拼装——`src/services/project-svc.mjs` 的 `registryStageLabel()` 把这六列拼成字符串数组，全为 0 时返回 `['未进入注册登记流程']`；看板的 `by_registry_stage` 则按从后往前的优先级归类（仅用于统计，不参与判断）。更新只能走 `updateProjectRegistry()` 的逐列白名单，禁止由外部传入任意列名。

### 4. 业主公示预计量 / 核查确定量 / 登记量三个数值分开存储

`project` 表用三个独立 `REAL` 列承载三个口径的减排量（单位均为 tCO2e），**不做合并、不做覆盖**：

- `owner_announced_estimate` —— 业主公示预计减排量，只有业主口径，不等于核查量；
- `verified_amount` —— 核查报告确定的量；
- `registered_amount` —— 登记量。

报告层强制分开表述：`src/services/report-svc.mjs` 的 `assembleReport()` 分别生成「业主公示预计减排量」与「核查确定的量 / 登记量」两条陈述，并对未登记项目附加「仅代表业主公示口径，不等于核查量或登记量」「未登记时不得表述为「已登记」」的说明。三个字段可各自为 NULL，NULL 的语义是「无记录」，不是 0。

### 5. 一切改变判断结果或导出数据的动作写 `audit_log`

`src/core/db.mjs` 导出 `audit(e)`，向 `audit_log` 追加一行（`id` 用 `newId('AUD')`，`at` 用 `nowIso()`）。已落地的审计动作包括：`project.create`、`project.registry_update`、`evidence.create`、`fact.create` / `fact.update`、`calculation.run`、`calculation.rejected`、`report.generate`、`report.export`、`report.export_denied`（导出被拒也留痕）、`review.decision`、`source.create`、`source_change.confirm`、`source.sync`、`alert.update`、`subscription.create`、`admin.set_gate_mode`、`seed.rebuild`。约定是：**任何会影响四态结论、数值结果、导出内容或保密边界的写操作都必须先写审计**；`audit_log` 只追加、不更新、不删除（删除能力也未在任何服务中暴露）。`result` 列区分正常与异常路径：默认 `ok`，拒绝出数记 `rejected`，越权导出记 `denied`。

### 6. 机器可执行的表达式与人类可读文本分列存放

`rule` 表把同一条件存两遍：`condition_text`（条件文本，人读）、`expression_text`（逻辑表达式，人读）、`expr`（JSON 表达式树，由 `src/rules/engine.mjs` 解释执行）。报告导出时引用前两者（可读性），判断时只使用 `expr`（确定性）。`required_fields` 同样是 JSON 数组，用于在事实缺失时把规则判为 `unknown` 而不是 `fail`。

### 7. 缺失数据不猜值，用 `unknown` 表达而不是 NULL 填充

`project_fact` 允许 `value_text` / `value_num` 同时为 NULL（字段已登记但取值未知），`rule` 求值结果因此有 `unknown` 态（`src/rules/engine.mjs` 的 `PASS` / `FAIL` / `UNKNOWN`）。`eligibility_run.conclusion` 由此产生「资料不足暂无法判断」这一独立结论，而不是把缺失数据当成通过或失败。

## 实体一览

| 表名 | 对应设计文档实体 | 职责 | 关键列 |
|---|---|---|---|
| `source_document` | SourceDocument（来源文档） | 官方来源库：方法学发布通知、管理办法、注册登记系统页面等；记录抓取时间与正文哈希 | `status`、`tier`、`is_official`、`original_file_hash`、`parse_quality` |
| `source_change` | SourceChange（来源变更记录） | 定时抓取后的差异与失败记录，供研究员确认后才生效 | `source_id`、`change_kind`、`review_status` |
| `methodology_version` | MethodologyVersion（方法学版本） | 方法学目录与版本；正式 / 草案 / 修订 / 废止各占一行，版本间用 `supersedes_id` 串联 | `methodology_id`、`version`、`document_status`、`catalog_confidence`、`is_candidate_eligible` |
| `rule` | Rule（规则卡规则） | 通用门槛与方法学专属条件的可执行规则；`methodology_version_id` 为 NULL 即通用门槛 | `methodology_version_id`、`layer`、`rule_id`、`expr`、`severity` |
| `formula` | Formula（公式） | 方法学公式及其单位、取整、适用期间、条款出处 | `methodology_version_id`、`formula_id`、`expression` |
| `factor_version` | FactorVersion（因子版本） | 排放因子与缺省系数库：取值、出处、年份、合理区间与核实状态 | `factor_key`、`value`、`methodology_version_id`、`scope`、`value_status` |
| `project` | Project（项目） | 项目档案主表：注册登记六状态分列、三套减排量数字分列、保密与团队归属 | `code`、`registry_*`（6 列）、`owner_announced_estimate`、`verified_amount`、`registered_amount` |
| `project_evidence` | Evidence（项目证据） | 证据文件与引用位置（页码、数据行、摘录），带保密等级 | `project_id`、`file_name`、`doc_type`、`page`、`excerpt`、`confidentiality` |
| `project_fact` | ProjectFact（项目事实） | 项目事实字段取值与来源分层，可指向证据 | `project_id`、`field_key`、`value_text` / `value_num`、`source_kind`、`evidence_id` |
| `fact_field` | FactField（项目事实字段字典） | 字段字典：分组、类型、单位、枚举、适用与必填范围、证据策略；前端表单与交付清单共用 | `key`、`value_type`、`applies_to`、`required_for`、`evidence_policy` |
| `match_run` | MatchRun（候选方法学匹配运行） | 一次候选匹配的完整结果快照（候选 / 观察项 / 排除项） | `project_id`、`analysis_base_date`、`result_json` |
| `eligibility_run` | EligibilityRun（申报条件检查运行） | 一次条件检查的四态结论、逐条判断与证据缺口快照 | `conclusion`、`methodology_version_id`、`result_json`、`review_status` |
| `calculation_run` | CalculationRun（情景计算运行） | 一次情景计算的输入、因子快照与结果；含被拒绝出数的运行 | `scenario`、`status`、`inputs_json`、`result_json`、`factor_snapshot_json` |
| `report` | Report（投资筛选报告） | 报告正文与运行快照引用；按 `revision` 递增，旧版本保留 | `revision`、`status`、`snapshot_json`、`content_json`、`supersedes_id` |
| `review_decision` | ReviewDecision（人工审核决定） | 对运行 / 报告 / 方法学版本 / 规则卡 / 插件的审核结论（多态对象） | `object_type`、`object_id`、`decision`、`reviewer`、`reviewer_role` |
| `alert` | Alert（信息雷达告警） | 目录缺口、草案跟踪、抓取失败、结构变化等告警与处置状态 | `kind`、`severity`、`status`、`methodology_id`、`source_id` |
| `subscription` | Subscription（订阅） | 按领域 / 区域 / 项目类型订阅提醒 | `domains`、`regions`、`project_types`、`channel`、`active` |
| `audit_log` | AuditLog（审计日志） | 一切改变判断结果或导出数据的动作留痕，只追加 | `at`、`actor`、`action`、`object_type`、`object_id`、`result` |
| `app_user` | User（用户） | 用户、角色与团队归属，授权与保密判断的依据 | `role`、`team_id`、`active` |
| `user_session` | UserSession（服务端会话） | 登录会话；只存令牌 SHA-256 摘要，过期 / 撤销即失效 | `token_hash`、`user_id`、`expires_at`、`revoked_at` |
| `system_meta` | SystemMeta（系统元数据） | 键值元数据：schema 版本、目录基线、出数门控模式、初始化时间 | `key`、`value`、`updated_at` |

## 表结构明细

以下逐表列出全部列。类型为 SQLite 的声明类型（SQLite 是动态类型，声明类型只影响类型亲和性）；「约束/默认值」列中未标注默认值的即无默认值、可为 NULL。

### source_document

官方来源库的每一份原文（方法学发布通知、管理办法、注册登记系统页面等）占一行，是全部方法学、规则与公告的可追溯起点。

| 列名 | 类型 | 约束/默认值 | 说明 |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | 来源 ID，`newId('SRC')` |
| `url` | TEXT | 可空 | 原文链接；定时同步只抓取 `url IS NOT NULL` 的来源 |
| `title` | TEXT | NOT NULL | 文档标题 |
| `issuing_authority` | TEXT | 可空 | 发布机关 |
| `doc_number` | TEXT | 可空 | 文号 |
| `publish_date` | TEXT | 可空 | 发布日期 `YYYY-MM-DD` |
| `effective_date` | TEXT | 可空 | 生效日期；草案必须为空 |
| `fetched_at` | TEXT | NOT NULL | 最近一次抓取时间（ISO 时间戳） |
| `original_file_hash` | TEXT | 可空 | 正文 sha256 哈希，作为变更比对基线；为空表示尚未建立基线 |
| `file_type` | TEXT | 可空 | 文件类型，种子数据统一为 `html` |
| `is_official` | INTEGER | NOT NULL DEFAULT 0 | 0/1，是否官方来源 |
| `tier` | INTEGER | NOT NULL DEFAULT 1 | 来源层级：1 一级来源，2 二级来源 |
| `status` | TEXT | NOT NULL | 文档状态枚举，见「状态枚举汇总」 |
| `parse_quality` | TEXT | 可空 | 解析质量：`good` / `partial` / `failed` |
| `parse_note` | TEXT | 可空 | 解析质量说明（例如动态渲染页面只能部分解析） |
| `local_path` | TEXT | 可空 | 原文本地留存路径 |
| `domain` | TEXT | 可空 | 所属领域，用于告警与订阅匹配 |
| `region` | TEXT | 可空 | 适用区域 |
| `created_at` | TEXT | NOT NULL | 记录创建时间 |
| `updated_at` | TEXT | NOT NULL | 记录更新时间 |

索引：
- `idx_source_status`：`(status)`
- `idx_source_publish`：`(publish_date)`

### source_change

定时抓取发现来源变化或抓取失败时追加一行，等待研究员确认；本表只记录差异，**不会自动修改方法学状态或规则卡**。

| 列名 | 类型 | 约束/默认值 | 说明 |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | 变更记录 ID，`newId('CHG')` |
| `source_id` | TEXT | NOT NULL, REFERENCES `source_document(id)` | 所属来源 |
| `detected_at` | TEXT | NOT NULL | 检测时间 |
| `change_kind` | TEXT | NOT NULL | 变更类型枚举，见「状态枚举汇总」 |
| `old_hash` | TEXT | 可空 | 变更前正文哈希 |
| `new_hash` | TEXT | 可空 | 变更后正文哈希；抓取失败时为 NULL |
| `diff_summary` | TEXT | 可空 | 差异摘要或失败原因（如 `HTTP 403`、`正文哈希变化`、`请求超时`） |
| `review_status` | TEXT | NOT NULL DEFAULT `'pending'` | 研究员确认状态 |
| `reviewed_by` | TEXT | 可空 | 确认人 |
| `reviewed_at` | TEXT | 可空 | 确认时间 |

索引：
- `idx_change_source`：`(source_id)`

### rule

规则卡中的一条规则。`methodology_version_id IS NULL` 表示通用门槛规则（对所有方法学生效），否则为方法学专属条件。

| 列名 | 类型 | 约束/默认值 | 说明 |
|---|---|---|---|

## 外键与删除策略

`PRAGMA foreign_keys = ON` 在每个连接上显式开启，因此下列外键是**强制生效**的（不开启时 SQLite 会静默忽略，这是最容易踩的坑）。

| `formula.methodology_version_id` | `methodology_version(id)` | 否 | 公式必须归属于某个方法学版本 |
| `project_evidence.project_id` | `project(id)` | 否 | 证据必须归属项目 |

| `eligibility_run.methodology_version_id` | `methodology_version(id)` | **是** | **NULL ⇒ 本次未找到可用的正式发布方法学**（结论为「无已发布适用方法学」） |
| `calculation_run.project_id` | `project(id)` | 否 | 计算运行必须归属项目 |
| `calculation_run.methodology_version_id` | `methodology_version(id)` | 否 | 计算必须绑定方法学版本（且必须为 `formal`） |
| `alert.source_id` | `source_document(id)` | 是 | 目录缺口类告警可能没有具体来源 |

**有意不加外键的列**（都是为了避免历史记录被删除牵连，或因为引用的是一组异质对象）：

- `factor_version.methodology_version_id` —— 该列没有 `REFERENCES`。它 `NOT NULL DEFAULT ''`，用**空串**表示全局因子，而不是 NULL。这样做有两个原因：全局因子不属于任何方法学版本；空串在 `UNIQUE(factor_key, methodology_version_id)` 中是普通值，可以正常参与唯一性判定（NULL 不行，见下一节）。
- `report.supersedes_id` —— 报告版本链，不加外键以免旧报告被删除时阻塞。
- `review_decision.object_id` / `audit_log.object_id` —— 多态对象引用，被审对象可能是方法学版本、规则卡、插件等不同表，无法用单条外键表达；且审核与审计记录必须长期保留，不应被对象删除影响。
- `project_evidence.evidence_id` 的反向引用：`project_fact.evidence_id` 有外键，但 `project_evidence` 不反向引用事实，避免循环。

**删除策略**：schema 中**没有任何 `ON DELETE` 子句**，因此全部外键都是默认的 `NO ACTION`（等价于 RESTRICT）：只要还有子行引用父行，删除父行就会被 SQLite 拒绝并报错。这意味着：

1. 正常业务代码**不删除**父行。参考数据需要重建时走 `src/services/seed.mjs` 的 `wipe()`：先 `PRAGMA foreign_keys = OFF`，按依赖顺序（子表在前，`audit_log`、`alert`、`subscription`、`review_decision`、`report`、`calculation_run`、`eligibility_run`、`match_run`、`project_fact`、`project_evidence`、`project`、`fact_field`、`factor_version`、`formula`、`rule`、`methodology_version`、`source_change`、`source_document`、`user_session`、`app_user`）逐表 `DELETE FROM`，随后恢复 `PRAGMA foreign_keys = ON`。注意 `system_meta` **不在** `TABLES` 列表里，因此重建参考数据不会清掉 schema 版本、认证模式与目录基线。
2. 若确需删除父行，必须在同一事务内按「子 → 父」顺序手工清理，或显式关闭外键检查后再删除，并在 `audit_log` 留痕。
3. `PRAGMA foreign_keys` 是**连接级**设置，不是数据库文件的持久属性（与 `journal_mode = WAL` 不同）。任何新的连接都必须自行设置，`db.mjs` 的 `getDb()` 已统一处理；如果绕过 `db.mjs` 直接开连接（例如写脚本导数据），必须自己再执行一次。

## 唯一约束与幂等性

schema 中的全部唯一性约束：

| 表 | 约束 | 语义 |
|---|---|---|
| `project` | `code UNIQUE` | 项目编号全局唯一 |
| `methodology_version` | `UNIQUE(methodology_id, version)` | 同一方法学编号下版本号不重复；草案与正式版靠 `version` 与 `document_status` 区分 |
| `rule` | `UNIQUE(methodology_version_id, rule_id)` | 同一方法学版本内规则编号唯一；通用门槛规则的 `methodology_version_id` 为 NULL |
| `formula` | `UNIQUE(methodology_version_id, formula_id)` | 同一方法学版本内公式编号唯一 |
| `factor_version` | `UNIQUE(factor_key, methodology_version_id)` | 同一归属下因子键唯一；全局因子的归属写空串 `''` |
| `project_fact` | `UNIQUE(project_id, field_key)` | 同一项目同一字段只有一行（`upsertFact()` 的 UPDATE 分支依赖它） |

此外所有表的 `TEXT PRIMARY KEY` 都是隐式唯一约束，`system_meta.key`、`fact_field.key` 为自然键主键；SQLite 会为每个 UNIQUE 与主键建立隐式索引（`sqlite_autoindex_*`），这不算显式索引。

### 已知微妙点：NULL 在唯一约束中互不相同

SQLite（以及 SQL 标准的默认行为）在唯一约束中把每个 NULL 都视为**互不相同**：`UNIQUE(a, b)` 允许多行同时满足 `a IS NULL` 且 `b` 相同。对本 schema 的具体影响：

- **`rule` 表**：通用门槛规则的 `methodology_version_id` 是 NULL。若直接对通用规则做「按唯一键 upsert」，SQLite 不会把它们当作冲突，`INSERT ... ON CONFLICT` 永远不会命中，重复执行就会插入一批**重复的通用门槛规则**。于是判断引擎按 `methodology_version_id IS NULL` 取通用规则时，同一规则会被求值多次，报告里出现重复条目，硬障碍计数也被放大。
- **`factor_version` 表刻意规避了这个问题**：`methodology_version_id` 定义为 `NOT NULL DEFAULT ''`，全局因子写空串 `''` 而不是 NULL，因此 `UNIQUE(factor_key, methodology_version_id)` 对全局因子同样生效，可以安全地重复写入。
- **`methodology_version` / `formula` / `project_fact` 不受影响**：这三张表的唯一键列全部 NOT NULL。

正因为 `rule` 的 NULL 无法参与唯一性判定，**`src/services/seed.mjs` 的 `seedAll()` 不采用 upsert，而是每次执行完整的参考数据重建**：

1. `wipe()`：关闭外键检查，逐表 `DELETE FROM`（顺序见「外键与删除策略」），再恢复外键检查；
2. `tx(() => { ... })`：在**单个事务**内重放全部参考数据——来源文档、方法学版本、字段字典、通用门槛规则、方法学规则卡、公式、因子版本、告警、用户、订阅——以及 `setMeta()` 写入的 `catalog_baseline`、`calculator_gate_mode`、`seeded_at`；
3. 事务内任意一步抛错即 `ROLLBACK`（`db.mjs` 的 `tx()` 实现），不会留下「清空了但没重建」的半成品库；
4. 事务提交后再写 `seed.rebuild` 审计日志；示例项目（`withDemo`）在另一个事务里单独写入。

`ensureSeeded()` 只在 `methodology_version` 为空时自动触发重建；其余场景（改规则卡、改因子、改字段字典后重新初始化）由 `node scripts/seed.mjs` 显式调用。**结论：参考数据表的幂等性由「全量重建 + 事务」保证，而不是由 upsert 保证。** 业务表（`project`、`project_fact`、各类 `*_run`、`report`）不走重建路径，各自用显式 upsert（`project_fact`）、`ON CONFLICT(key) DO UPDATE`（`system_meta`）或纯追加（运行与报告）保证语义正确。

## 数据保留与版本快照

因子库与方法学库会持续更新（新因子、新版本、原值修订），但**历史报告与历史运行结果不得被静默改写**。这由五个 JSON 列 + 三个关系列共同保证：

| 存储 | 内容 | 作用 |
|---|---|---|
| `calculation_run.factor_snapshot_json` | 本次运行实际读取到的因子快照数组（`factor_key`、`name`、`value`、`unit`、`value_status`、`source_ref`、`source_year` 等） | 把「算的时候用的是哪一版因子」固化在运行记录里；`factor_version` 之后怎么改都影响不到它 |
| `calculation_run.inputs_json` | `{ inputs, origins, overrides }`：解析后的输入值、每个输入的来源说明（官方已确认 / 项目资料记载 / 业主自述 / 分析师录入 / 模型假设 / 因子缺省 / 插件缺省）、用户情景覆盖项 | 支撑报告中的来源分层标注与后续差异解释 |
| `calculation_run.result_json` | 结果数值、计算步骤、情景乘数与说明、警告、占位系数清单、门控模式、免责声明，以及**方法学身份快照**（`methodology_id`、`code_display`、`name`、`version`、`official_url`、`effective_date`） | 结果自解释：即使 `methodology_version` 名称或状态后来变了，旧运行的叙述仍指向当时的版本信息 |
| `eligibility_run.result_json` | 四态结论、`summary` 统计、`layers`（common / specific / conflict 的逐条状态与依据）、`gap_list`、`priority_gaps`、`calculation_availability`、`match_snapshot`、`methodology_version` 快照 | 条件检查结论同样自包含，可复算可追溯 |
| `report.snapshot_json` | 运行指针：`eligibility_run_id`、`match_run_id`、`calculation_run_ids`、`methodology_version_id`、`analysis_base_date`、`generated_at` | 报告与运行的一对多引用关系；配合 `*_run.result_json` 即可完整还原当年结论 |
| `report.content_json` | 装配完成的报告全文（一页结论、正文八节、可追溯索引、免责声明） | 报告正文本身冻结在生成时刻，导出不重新计算 |
| `report.revision` + `report.supersedes_id` | 版本号（同项目内递增）与上一版 ID | 报告修订是**新增行**，旧版本原样保留，链条可回溯 |

配套的服务层行为：

- **`src/services/calc-svc.mjs` 的 `compareRuns(idA, idB)`** 是「历史不被改写」的直接验证工具：它通过 `getCalculationRun()` 读两次运行，解析 `inputs_json` / `result_json` / `factor_snapshot_json`，逐项比对输入差异与因子差异（比较 `value` 与 `value_status`），计算 `er_annual` 的绝对差与百分比差，并用 `buildDiffExplanation()` 给出可读原因（方法学版本变化、分析基准日变化、情景变化、输入参数变化、因子变化）。关键是：**方法学身份取自 `result_json.methodology` 而不是 JOIN `methodology_version`**，因子值取自 `factor_snapshot_json` 而不是 JOIN `factor_version`，所以库更新后对比两次历史运行，得到的仍是「当时各自用了什么」的忠实差异，函数末尾也明确返回 `note: '历史运行结果与其因子快照被完整保留，库更新不会静默改写历史报告。'`
- **`src/services/report-svc.mjs` 的 `generateReport()`** 每次都插入新的 `report` 行：`revision = prev.revision + 1`（首版 1），`supersedes_id = prev.id`，`status = 'draft'`，同时把当次 `eligibility_run_id` / `match_run_id` / `calculation_run_ids` 写进 `snapshot_json`。它**不会 UPDATE 旧报告行**。
- **`exportReport()`** 只读 `report.content_json` 与 `project` 基本信息，不重跑判断与计算，因此同一 `report_id` 任何时候导出内容一致；导出与被拒导出都写审计。
- **`decideReview()`** 是唯一会 UPDATE 既有运行/报告的路径，且只动状态列（`calculation_run.audit_status` / `review_status`、`eligibility_run.review_status`、`report.status`），**从不修改任何数值或 JSON 快照**。
- **方法学版本表**本身也是快照友好设计：新版本新增一行（`UNIQUE(methodology_id, version)`），废止只写 `repeal_date` 与新版的 `document_status`，旧行的 `document_status` 不就地翻转。

结论：只要不改这三类 JSON 列，因子库与方法学库的日常更新（新增版本、修订取值、废止旧版）都无法影响已生成的 `eligibility_run`、`calculation_run` 与 `report`；需要「重新判断」时是**再跑一次并生成新报告**，新旧并列，差异由 `compareRuns()` 解释。

## 数据量与索引建议

面向机构内网部署（单机、单进程 Node 服务、SQLite 文件库）的实操建议：

### 规模预期

- **参考数据表很小且稳定**：`methodology_version` 约 17–20 行、`rule` 约 100–300 行（通用门槛 + 4 套规则卡）、`formula` 与 `factor_version` 各几十行、`fact_field` 约 60 行、`source_document` 几十行。这些表全表扫描都在毫秒级，无需额外调优。
- **业务表随项目数线性增长**：`project_fact` 每项目约 30–60 行，`project_evidence` 每项目几十行。
- **真正会涨的是追加型表**：`match_run`、`eligibility_run`、`calculation_run`、`report`、`audit_log`。其中 `calculation_run.result_json` 与 `report.content_json` 是最大的文本列（单行从几十 KB 到数百 KB 量级，因为要装下逐条规则判定、计算步骤、因子快照与报告全文）。粗算：50 个项目 × 每项目数十次运行/报告 × 0.1 MB ≈ 数百 MB 量级。若 5 年内不超过 10 万项目、百万次运行，单文件 SQLite 完全够用。

### 现有索引已覆盖的高频查询

schema 已为全部高频过滤条件建了索引，**不建议在项目早期再加**（写放大与维护成本不划算）：

- 运行与报告按项目查历史：`idx_match_project`、`idx_elig_project`、`idx_calc_project`、`idx_report_project`——这四个是访问最频繁的索引，看板、项目详情、报告生成都按 `project_id` 查。
- 审计追溯：`idx_audit_at`（按时间倒序翻页）、`idx_audit_object`（按对象查变更历史）。
- 审核待办：`idx_review_object`（多态对象查询）；`listPendingReviews()` 还按 `review_status = 'pending'` / `report.status = 'draft'` 过滤，这两列目前没有单独索引，但在待办条目有限（各查询 `LIMIT 100`）时影响可忽略。
- 来源与告警：`idx_source_status`、`idx_source_publish`、`idx_change_source`、`idx_alert_status`。
- 方法学与规则：`idx_mv_status`、`idx_mv_mid`、`idx_rule_mv`、`idx_rule_layer`、`idx_factor_key`。
- 团队授权：`idx_project_team`；`project.code` 的唯一索引同时服务编号精确查询。

若后续数据量显著上升，第一优先是给 `calculation_run.review_status`、`eligibility_run.review_status`、`report.status` 补单列索引（待办列表），其次是按 `project_id, run_at DESC` 建复合索引替换现有单列索引；`rule(methodology_version_id IS NULL)` 这类「通用规则」查询依赖 `idx_rule_mv` 即可（NULL 也在索引中）。

### 索引与写入的权衡

- 添加索引会拖慢 `seedAll()` 的全量重建与 `audit_log` 的追加，而审计日志是最热的写路径。除非确证慢查询，否则保持现状。
- `EXPLAIN QUERY PLAN` 是排障首选；SQLite 没有统计信息自动收集，schema 变更后可用 `ANALYZE` + `PRAGMA optimize` 更新。

### WAL、并发与备份

- **WAL 模式**下读不阻塞写、写不阻塞读，但同一时刻仍只允许一个写事务。Node 服务是单进程、`DatabaseSync` 是同步 API，天然串行，不会出现多写者争用。**不要**让第二个进程（例如另一个脚本实例）长期写同一个库文件；`seedAll()` 这类重建操作应停服执行，或至少确认没有并发的写请求。
- WAL 会额外产生 `data/ccer.db-wal` 与 `data/ccer.db-shm` 两个文件。备份时**先做检查点**（`PRAGMA wal_checkpoint(TRUNCATE)`）再复制，或使用 SQLite 的在线备份接口；只复制主库文件可能丢掉尚未回写的已提交事务。
- 数据库文件应放在**本机 SSD**，不要放在 SMB/NFS 网络共享上：SQLite 的锁机制在网络文件系统上不可靠，且会显著放大延迟。内网部署的「共享」需求应通过应用接口实现，而不是共享库文件。
- 长事务（尤其是 `seedAll()` 的重建事务）会阻塞 WAL 检查点并让 `-wal` 文件膨胀；重建完成后建议做一次检查点。
- **验收与迁移**：`system_meta.schema_version` 当前为 `1.0.0`。由于 `migrate()` 每次连接都重放 `CREATE TABLE IF NOT EXISTS`，新增列/新增表需要通过单独的迁移语句实现（当前版本尚未引入迁移框架，`ALTER TABLE ADD COLUMN` 需注意 SQLite 对默认值与 NOT NULL 的限制）。

### 归档与保留

- `audit_log` 是只增表，长期运行后是行数最多的表。建议按年归档：先导出 `at < 年初` 的行到只读归档库或文件，再删除主库中的对应行（删除自身也要写一条审计）；不建议改成覆盖写。
- `calculation_run.result_json`、`report.content_json` 属于法律与追溯意义上的证据，**不建议压缩或裁剪**；若确实需要控制体积，优先归档已 `superseded` 的旧报告与对应运行（连同其 `factor_snapshot_json` 一并导出，保持「快照成套」），而不是删除单个 JSON 列。
- 定期备份 + 定期做一次「从备份恢复并跑 `test/02-acceptance.test.mjs` 与 `test/03-calculation.test.mjs`」的演练，是验证备份可用性的最低成本方式。
