## 二、如何运行

```bash
cd "D:\AI workspace\ccer-screening"
npm run seed        # 初始化数据库
npm start           # → http://127.0.0.1:8787
npm test            # 66 项自动化测试
```

零第三方依赖，无需 `npm install`。要求 Node.js ≥ 22.5.0。

启动后建议的体验路径：

1. 打开 **总览看板** —— 看方法学目录结构、项目结论分布、告警与门禁模式。
2. 打开 **项目档案与筛选** → 点击 `CCER-DEMO-001 山西晋城某煤业低浓度瓦斯发电项目`
   → 依次走 **候选方法学匹配 → 申报条件检查 → 减排量初算 → 投资筛选报告**。
3. 回到项目列表 → 打开 `CCER-DEMO-002`（开工日期缺失）与 `CCER-DEMO-004`（站场规模超限）
   → 对比两者的四态结论差异，理解「待核实」与「存在明确障碍」的区别。
4. 顶栏右上角把身份切换到 **其他团队成员（viewer）** → 重新打开 `CCER-DEMO-001`
   → 体验项目级授权拒绝。
5. 打开 **管理后台** → 查看 4 个计算插件的占位系数明细 → 切换到**严格模式**
   → 回到项目详情重跑计算，观察「暂不支持自动测算」的阻断效果。

## 五、本次交付中值得留意的三个设计决策

### 5.1 把「证据不足」做成引擎的一等公民，而不是提示文案

`FactStore.usable(field, evidencePolicy)` 是「待核实」的唯一实现点，有五个明确的降级分支
（字段缺失 / 值为空 / 来源为模型假设 / 严格证据不符 / 证据记录不存在）。
这意味着「业主说项目不承担法定减排义务」这种情形，系统会**拒绝**给出「通过」，
而不是给一个通过再加一句提示。验收用例 2 就是为此设计的。

### 5.2 规则引擎使用 JSON 表达式树而非自然语言或 `eval`

规则同时存储人读的 `expression_text` 和机器执行的 `expr` JSON 树。
执行只依赖 `expr`，因此不存在「自然语言被曲解」的空间；
未知算子、非法节点、求值异常一律返回「待核实」而非「不通过」——
系统的失败模式被设计成「不敢下结论」而不是「错误地下结论」。

### 5.3 目录完整性差异被显式暴露，而不是静默补齐

设计文档记载官方目录有 18 项方法学，本库录入了 17 项，其中 9 项只有主管部门答记者问口径、
编号未从发布通知核实。系统**没有**推测这 9 个编号，而是：

- 把它们的 `code_display` 置空并标记 `catalog_confidence = 'name_only_pending_code'`
- 置 `is_candidate_eligible = 0`，使其只可检索、不可成为候选
- 生成 `catalog_gap` 告警，在总览看板与信息雷达持续提示差额
- 在 `docs/05-方法学清单.md` 中逐项列出待核实清单（EXP-301 ~ EXP-310）

这与设计文档第 11 节「不得把网页搜索摘要当作规则源」「不得用 AI 自行生成未经核实的系数或公式」一致。

## 七、⚠️ 阻断项与使用限制（必须阅读）

### 7.1 两个阻断正式使用的条件

| 编号 | 条件 | 影响 | 解除方式 |
|---|---|---|---|
| **阻断 1** | 33 条公式的 `clause_ref` 均为 `【占位】`，未回填方法学原文条款页码 | 报告无法引用条款，不满足「每项判断可追到原文条款」的验收标准 | 领域专家对照方法学 PDF 逐条回填（EXP-101/111/121/131） |
| **阻断 2** | 17 项方法学专属缺省系数标记为 `placeholder`，未经领域专家确认 | 测算结果不具正式效力 | 领域专家逐项确认后改为 `verified`（EXP-102~106 等） |

**在这两项解除之前**：

- 系统输出**只能用于内部讨论、流程验证与演示**。
- 不得对外出具报告，不得用于投资决策，不得提交监管机构。
- 严格模式下这些插件会被**阻止出数**并提示「暂不支持自动测算」——这是正确行为。
- 演示模式下虽可出数，但每个输出都会逐项标注占位系数与对应的 EXP 编号。

### 7.2 其他已知限制

| 限制 | 说明 |
|---|---|
| 目录完整性 | 本库 17 项方法学，设计基线 18 项，差额 1 项待核对；9 项编号待核实 |
| 规则卡覆盖 | 仅首批 4 项甲烷类方法学已建规则卡（33 条专属条件），其余 13 项显示「暂不支持自动判断」 |
| 自动证据抽取 | **未实现**。证据由人工录入文件名、页码与原文片段；无 OCR / 文档解析服务 |
| 文件归档 | **未实现**。PDF 原件未下载归档，`original_file_hash` 列已就绪 |
| 敏感附件加密 | **未实现**。仅有访问控制与审计，无静态加密 |
| 身份认证 | 已改为**服务端会话**（`user_session` + 令牌 SHA-256 摘要）：`x-user-id` / `?user=` 在默认 `session` 模式下被完全忽略，未认证 `/api/*` 返回 401。**但登录口令仍是占位演示口令**（`src/data/users.mjs`），生产部署必须接入机构统一身份认证（SSO / OIDC / LDAP） |
| 二进制导出 | 未生成严格 OOXML 的 `.docx` / `.xlsx`。已提供 **Word（`.doc`）与 Excel（`.xls`）** 两种 HTML 形式的 Office 导出（Word / Excel / WPS 可直接打开并编辑），另有 Markdown、HTML（可打印为 PDF）、CSV，共 **5 种格式** |
| 批量导入与重跑 | 接口层未实现 |
| 大模型能力 | 系统**不调用任何外部大模型 API**。字段抽取、变更摘要、报告草稿全部由人工录入与确定性模板实现，以换取完全离线可运行与数据不外流 |

### 7.3 意图明确的设计取舍

设计文档第 8 节提到「LLM 只进入抽取、检索解释、变更摘要和报告草稿环节」。
本次交付**没有**接入 LLM，而是把这三个环节落在确定性代码与人工录入上：

| LLM 的潜在职责 | 本次实现 | 取舍理由 |
|---|---|---|
| 字段抽取 | 人工在项目档案录入 + 证据定位 | 完全离线可运行；无项目数据外流风险；抽取结果天然可追溯 |
| 检索解释 | SQL 检索 + 规则卡结构化字段 | 结论可复算，不依赖模型版本 |
| 变更摘要 | 内容哈希比对 + 研究员填写 `diff_summary` | 避免把网页摘要当作规则源（设计文档明令禁止） |
| 报告草稿 | `assembleReport()` 模板函数 | 五级来源标注由代码强制保证，不会遗漏 |

若机构后续决定接入 LLM，只需替换上述四个入口，判断引擎与计算插件链路不受影响。
