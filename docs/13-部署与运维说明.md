# 部署与运维说明

> 面向机构内网管理员。覆盖环境要求、部署步骤、管理员操作、备份恢复、故障排查与安全检查单。

---

## 一、环境要求

| 项 | 要求 | 检查命令 |
|---|---|---|
| Node.js | **≥ 22.5.0**（需要内置 `node:sqlite`）；实测 24.14.1 | `node -v` |
| 操作系统 | Windows 10/11、Windows Server 2019+、Linux（x64/arm64） | — |
| 第三方依赖 | **无**。`npm install` 无需执行（`dependencies` 与 `devDependencies` 均为空） | `npm ls --depth=0` |
| 磁盘 | 初始 < 5 MB；运行记录按每项目每月约 0.5 MB 估算 | — |
| 内存 | < 100 MB | — |
| 浏览器 | Chromium 内核或 Firefox 最新版（ES Module + `fetch` + `AbortController`） | — |
| 网络 | 除「信息雷达」的来源抓取外**无需外网**。抓取须经机构受控出口 | — |

> **离线部署**：直接把整个 `ccer-screening` 目录拷贝到目标机器即可。不需要联网安装任何包。

## 二、部署步骤

### 2.1 首次部署

```bash
# 1) 进入目录
cd "D:\AI workspace\ccer-screening"

# 2) 初始化数据库并写入方法学目录、规则卡、因子与 5 个演示项目
npm run seed

# 3) 生成两份待确认交付物
node scripts/gen-docs.mjs

# 4) 运行测试，确认环境正常（66 项应全部通过）
npm test

# 5) 启动服务
npm start
```

启动后控制台输出：

```text
  CCER 投资筛选 AI 应用已启动
  ─────────────────────────────────────────────
  工作台地址：http://127.0.0.1:8787
  接口健康检查：http://127.0.0.1:8787/api/health
  数据库：D:\AI workspace\ccer-screening\data\ccer.db
  计算插件门禁模式：demo
```

### 2.2 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `PORT` | `8787` | 监听端口 |
| `HOST` | `127.0.0.1` | 监听地址。改为内网地址时**必须**同时设置 `CCER_ALLOW_REMOTE=1` |
| `CCER_DB_PATH` | `<项目目录>/data/ccer.db` | 数据库文件路径 |
| `CCER_ALLOW_REMOTE` | 未设置 | 设为 `1` 才允许非回环访问。**这是有意设计的双重确认** |
| `CCER_AUTH_MODE` | 未设置（取系统元数据 `auth_mode`，默认 `session`） | 认证模式覆盖：`session`（身份只来自服务端会话，**生产必须使用**）或 `dev`（关闭认证，仅本地演示）。设为 `dev` 时服务启动会打印醒目警告横幅；`dev` + `CCER_ALLOW_REMOTE=1` 的组合会**拒绝启动** |

> ⚠️ **认证模式**：默认 `session` 模式下，请求头 `x-user-id` 与查询参数 `?user=` 被**完全忽略**，
> 未携带有效会话（`Authorization: Bearer` 或 Cookie `ccer_session`）的 `/api/*` 请求一律返回 401。
> 不要把 `CCER_AUTH_MODE=dev` 写进任何生产配置文件或服务单元。

### 2.3 生产启动（Windows 服务 / Linux systemd）

**Windows**——用任务计划程序或 NSSM 注册为服务：

```powershell
$env:CCER_ALLOW_REMOTE = "1"
Start-Process node -ArgumentList "src/server.mjs" -WorkingDirectory "D:\AI workspace\ccer-screening" -WindowStyle Hidden
```

**Linux systemd**：

```ini
# /etc/systemd/system/ccer-screening.service
[Unit]
Description=CCER 投资筛选 AI 应用
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/ccer-screening
Environment=NODE_ENV=production
Environment=HOST=0.0.0.0
Environment=CCER_ALLOW_REMOTE=1
Environment=PORT=8787
ExecStart=/usr/bin/node src/server.mjs
Restart=on-failure
RestartSec=5
User=ccer

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now ccer-screening
```

### 2.4 反向代理（可选）

如机构要求 HTTPS 与统一入口，在 Nginx 前置：

```nginx
server {
  listen 443 ssl;
  server_name ccer.internal.example.com;
  ssl_certificate     /etc/ssl/ccer.crt;
  ssl_certificate_key /etc/ssl/ccer.key;

  location / {
    proxy_pass http://127.0.0.1:8787;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header Authorization $http_authorization;   # 透传会话令牌
    proxy_set_header Cookie $http_cookie;                 # 透传 ccer_session
  }
}
```

> ⚠️ **安全提示**：服务默认以**服务端会话**识别身份（`auth_mode = session`）。
> 客户端传入的 `x-user-id` 与 `?user=` 一律被忽略，因此**不要**再配置
> `proxy_set_header x-user-id …`（无任何效果，且容易误导运维以为身份来自代理）。
> 会话令牌通过 `Authorization: Bearer` 或 HttpOnly Cookie `ccer_session` 回传，反向代理必须原样透传；
> 会话本身仍由应用在 `user_session` 表中校验，代理不承担鉴权职责。
> 生产部署还须把 `src/data/users.mjs` 的演示口令替换为机构统一身份认证（OIDC / LDAP）。
> 见第八节安全检查单。

## 三、管理员操作手册

### 3.1 日常：来源变更确认

1. 打开 **信息雷达** 页。
2. 查看「来源变更记录（待研究员确认）」表。
3. 按变更类型处置：

| 变更类型 | 处置动作 |
|---|---|
| `content_revised` | 打开来源链接阅读变更 → 若影响方法学适用条件/公式/因子，按 3.3 更新规则卡或因子 → 点「确认」 |
| `new` | 在[注册登记系统](https://ccer.cets.org.cn/)核对编号与名称 → 在 `src/data/catalog.mjs` 补录 → `npm run seed` → 点「确认」 |
| `fetch_failed` | 检查站点可达性与受控出口策略；若公告撤回，更新来源 `status` → 点「确认」 |
| `draft_consultation` | **保持草案状态**，建立跟踪；绝不替换现行正式版本 |

4. 点「确认」会写入 `source_change.review_status` 并留审计日志。

> **系统不会自动把抓取结果发布到判断引擎。** 这是设计文档第 4 节的硬性要求。

### 3.2 日常：人工审核

打开 **人工审核** 页，处理三类待审项：

| 类别 | 审核要点 |
|---|---|
| 待审核计算运行 | 逐式明细是否与方法学一致；占位系数是否已确认；敏感性是否合理 |
| 待复核条件检查 | 每条规则的事实值、证据定位、条款引用是否正确 |
| 待审报告 | 结论与依据是否一致；三套数字表述是否规范；是否可对外沟通 |

审核结论：**通过** / **要求补充** / **驳回**。三者都会写入 `review_decision` 并改变对应记录的复核状态。

### 3.3 管理员：更新方法学或规则

```bash
# 1) 编辑目录数据（必须附官方发布通知 URL）
notepad src/data/catalog.mjs

# 2) 编辑某方法学的规则卡与计算插件
notepad src/methodologies/ccer-10-001.mjs

# 3) 重建数据库（会清空全部数据，包括项目与运行记录！）
npm run seed -- --reset

# 4) 回归测试
npm test

# 5) 重新生成待确认交付物
node scripts/gen-docs.mjs
```

> ⚠️ `npm run seed -- --reset` 会**删除** `data/ccer.db`。在已有真实项目数据后，
> 应先备份（见第四节），再考虑改用「只重建参考数据」的方式：
> 编辑 `scripts/seed.mjs` 或直接调用 `seedAll({ withDemo: false })` 前先导出项目数据。

### 3.4 管理员：切换计算门禁模式

**管理后台** 页 → 「计算插件门禁模式」→ 点「切换为严格模式 / 演示模式」。
仅 `admin` 角色可操作，动作记入审计日志（`admin.set_gate_mode`）。

| 模式 | 行为 | 适用场景 |
|---|---|---|
| **演示模式**（`demo`，默认） | 允许出数，但输出逐项标注占位系数 | 内部演示与流程验证 |
| **严格模式**（`strict`） | 只要插件含任一 `placeholder` 因子即拒绝出数，提示「暂不支持自动测算」 | **正式使用**；符合设计文档要求 |

**切换到严格模式的前置条件**：`docs/12-领域专家确认清单.md` 中全部 EXP 条目确认完毕。
可用以下命令检查剩余占位因子：

```bash
node -e "import('./src/methodologies/index.mjs').then(m=>{for(const x of m.listMethodologyModules()){const p=x.plugin.factors.filter(f=>f.value_status==='placeholder');console.log(x.meta.methodology_id, p.length? p.length+' 项待确认': '已全部确认')}})"
```

当前输出应为：4 个方法学各 3–4 项，**合计 17 项待确认**。

### 3.5 管理员：标准与依据编码维护

**管理后台** 页底部展示 `src/data/standard-codes.mjs` 中的标准编码表。
标为「待核实」的条目（GB/T 32150、GB/T 32151 系列）在编号核实前**不得**用于计算口径判定。

## 四、备份与恢复

### 4.1 备份

```bash
# 备份到 data/backups/，保留最近 30 份
npm run backup

# 指定目录并只保留 10 份
node scripts/backup.mjs --out D:\ccer-backup --keep 10
```

备份产物：

| 文件 | 内容 |
|---|---|
| `ccer-<时间戳>.db` | SQLite 一致性快照（用 `VACUUM INTO` 生成，已合并 WAL） |
| `ccer-<时间戳>.catalog.json` | 参考数据 JSON 快照（来源、方法学、规则、公式、因子、字段字典、项目清单、系统元数据、各表记录数） |
| `manifest.json` | 备份清单，含每份的 SHA-256、大小、记录数与门禁模式 |

### 4.2 校验

```bash
node scripts/backup.mjs --verify "data\backups\ccer-2026-09-24T10-30-00.db"
```

输出 SHA-256 并与 `manifest.json` 中的记录比对；一致则退出码 0，不一致则 2。

### 4.3 恢复

```bash
# 1) 停止服务
# 2) 备份当前库（以防万一）
Move-Item data\ccer.db data\ccer.db.broken

# 3) 恢复快照
Copy-Item "data\backups\ccer-2026-09-24T10-30-00.db" data\ccer.db

# 4) 清理可能残留的 WAL 文件
Remove-Item data\ccer.db-wal, data\ccer.db-shm -ErrorAction SilentlyContinue

# 5) 启动并核对
npm start
# 访问 /api/health 与 /api/dashboard 确认数据完整
```

### 4.4 备份策略建议

| 频率 | 保留 | 介质 |
|---|---|---|
| 每日自动（计划任务） | 30 份 | 本机 `data/backups/` |
| 每周 | 12 份 | 机构文件服务器 |
| 每月 | 24 份 | 异地 / 冷存储 |

同时应归档 `docs/` 与 `src/data/*.mjs`（参考数据的可读版本），
因为 JSON 快照便于人工核对，而 `.db` 快照便于快速恢复。

## 六、故障排查

| 症状 | 原因 | 处置 |
|---|---|---|
| `Error: ENOENT ... schema.sql` | 工作目录不对 | 在项目根目录执行，或用 `workdir` 指定 |
| `403 本服务默认仅允许回环访问` | 从其他机器访问 | 设置 `HOST=0.0.0.0` 与 `CCER_ALLOW_REMOTE=1`，并确认已配置身份认证 |
| `SQLITE_ERROR: database is locked` | 多个进程同时写同一数据库 | 确保只运行一个服务进程；`data/` 放在本地磁盘而非网络共享 |
| 启动时报 `ExperimentalWarning: SQLite` | Node 的特性提示，非错误 | 可忽略；如需静默，加 `--no-warnings` |
| 接口返回 500 且 `message: ambiguous column name` | SQL 列名歧义 | 查看服务端 stderr 的堆栈（含前 4 帧），修复对应 `SELECT` 的列限定 |
| 计算返回 422 | 输入校验未通过（这是**正常业务结果**） | 阅读响应中的 `errors[].message`，按提示补齐或修正；`field` 指明原始字段名 |
| 计算返回 409「暂不支持自动测算」 | 严格模式且插件含占位系数；或该版本无插件 | 在管理后台查看插件状态；确认系数后再切严格模式 |
| 报告导出乱码 | CSV 未按 UTF-8 打开 | CSV 已带 BOM，用 Excel「数据 → 从文本」并选 UTF-8，或直接打开 |
| 前端页面空白 | 浏览器不支持 ES Module | 升级浏览器；打开控制台查看具体错误 |
| `npm test` 报 `spawn EPERM` | 受限沙箱阻止测试运行器派生子进程 | 用 `npm test`（已改为逐文件进程内执行）；不要用 `node --test test/` |

## 八、安全检查单（上线前逐项确认）

- [ ] **网络暴露**：仅在机构内网可访问；如对非回环开放，已确认 `CCER_ALLOW_REMOTE=1` 是有意为之
- [ ] **认证模式**：已确认运行在 `session` 模式（`GET /api/health` 返回 `auth_mode: "session"`），且服务单元与启动脚本中**没有** `CCER_AUTH_MODE=dev`
- [ ] **自报身份失效**：已实测「不带令牌仅带 `x-user-id: user-admin`」的请求返回 **401**（原漏洞的回归验证）
- [ ] **会话安全**：`user_session` 中只保存令牌摘要；已确认 `GET /api/admin/sessions` 不返回 `token_hash`
- [ ] **身份认证**：已把 `src/data/users.mjs` 的演示口令替换为机构统一身份认证（SSO / OIDC / LDAP），并删除明文口令字段
- [ ] **HTTPS**：已由反向代理提供 TLS（HttpOnly Cookie 在 HTTPS 下应由代理补 `Secure` 属性）
- [ ] **项目授权**：已按机构实际团队划分核对 `project.team_id` 取值
- [ ] **附件保密**：已核对标为 `restricted` 的证据附件范围；受限角色抽查不可见
- [ ] **导出审计**：已确认 `report.export` 与 `report.export_denied` 均写入审计日志
- [ ] **审计留存**：已确认 `audit_log` 的留存周期符合机构要求，必要时外送 SIEM
- [ ] **数据外流**：已确认除信息雷达抓取外无其他出站请求；已确认系统不调用外部大模型 API
- [ ] **受控出口**：已为生态环境部 / 注册登记系统域名配置代理白名单
- [ ] **敏感附件静态加密**：⚠️ **当前未实现**。如机构要求，须在文件服务层引入 AES-GCM 加密（见 `docs/01` G-05）
- [ ] **备份**：已配置定时备份与异地归档；已演练一次恢复流程
- [ ] **门禁模式**：⚠️ 在 `docs/12` 全部 EXP 条目确认前，**必须保持** `demo` 并在界面显著提示占位系数；
      确认完毕后切换为 `strict`
- [ ] **口径确认**：`docs/12-领域专家确认清单.md` 已由领域专家签署
- [ ] **免责声明**：已确认报告与工作台均显示使用边界与免责声明

## 九、升级与回滚

```bash
# 1) 备份
npm run backup -- --out D:\ccer-backup\pre-upgrade

# 2) 替换代码（保留 data/ 目录）

# 3) 若 schema 有变更，执行迁移（当前 schema 全部为 CREATE TABLE IF NOT EXISTS，幂等）
npm run seed:keep      # 只重建参考数据，保留项目数据？——见下方说明

# 4) 回归测试
npm test

# 5) 重启服务
```

> ⚠️ **注意**：`npm run seed:keep` 当前会调用 `wipe()` 清空全部表后再写入参考数据，
> **同样会删除项目数据**。若需在升级时保留项目数据，请：
> 1. 用 `npm run backup` 备份；
> 2. 升级后先启动服务（空库不会被自动种子化，因为参考表已有数据）；
> 3. 手工重放项目数据，或编写一次性迁移脚本把旧库的 `project` / `project_fact` /
>    `project_evidence` / 运行记录 / 报告导入新库（表结构未变，可直接 `ATTACH` 后 `INSERT ... SELECT`）。
