## 二、阶段划分（A / B / C / D）

设计文档第 10 节定义了四个阶段。本次交付一次性打通 A → D，但各阶段的完成深度不同。

### 阶段 A：基础库

**交付物**：官方来源采集、文件归档、方法学目录、状态与版本管理、权限

| 验收标准 | 达成情况 | 验证方式 |
|---|---|---|
| 官方目录可核对 | ✅ 8 条一级来源，全部标注 URL / 发布机关 / 文号 / 日期；方法学编号以发布通知为准 | `docs/05-方法学清单.md` 第八节；`GET /api/sources` |
| 新增 / 修订 / 草案不混淆 | ✅ `document_status` 四态分列；两份 2026 修订征求意见稿与现行正式版并存 | 测试「正式 / 征求意见 / 修订 / 废止 分列存储，绝不互相覆盖」；验收用例 1 |
| 每条记录可打开原件 | ✅ `source_document.url` 与 `methodology_version.official_url` | `GET /api/methodologies` 返回 `official_url`；详情页「打开官方原文」 |

| 验收标准 | 达成情况 | 验证方式 |

### 用例 1 的一个额外发现（已在测试中固化）

用「造林碳汇」项目验证用例 1 时，系统给出的结论是 **「无已发布适用方法学」**，
而不是「可继续尽调」。原因是：`CCER-14-002-V01` 虽为正式发布版本，但**尚未建立规则卡**，
因此被排除出候选清单（`reason_code = rulecard_not_approved`），草案也只作观察项。

这恰好验证了设计文档第 5 节的要求：**「没有获批规则卡的方法学可供检索，但不可显示为『已完成条件检查』」**。
测试同时断言了排除理由的存在与内容。

### 测试环境的隔离

每个测试文件使用独立临时数据库（`test/helpers.mjs` 中设置 `CCER_DB_PATH` 到系统临时目录），
测试结束删除，**不污染演示库**。

### 关于 `node --test`

Node 的测试运行器会为每个测试文件派生带管道的子进程，在受限沙箱环境中会被拒绝（`spawn EPERM`）。
因此 `package.json` 的 `test` 脚本改为按文件顺序在**进程内**执行：

```json
"test": "node test/01-rule-engine.test.mjs && node test/02-acceptance.test.mjs && node test/03-calculation.test.mjs && node test/04-catalog-and-governance.test.mjs"
```

在不受限环境中 `node --test test/` 同样可用，效果一致。
